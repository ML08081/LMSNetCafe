# 人脸认证模块设计

## 1. 模块目标

人脸认证用于提高会员上机身份核验能力，主要解决以下问题：

- 防止会员账号被他人冒用。
- 减少前台人工核验成本。
- 为上机记录提供身份验证日志。

该模块不作为唯一身份依据，识别失败时允许前台根据业务规则进行人工处理。

## 2. 技术方案

建议将人脸认证拆为独立 Python 服务：

- Web 框架：FastAPI。
- 图像处理：OpenCV。
- 特征提取：InsightFace、face-recognition 或可替换模型。
- 存储方式：后端业务库保存档案元数据，人脸服务保存或返回特征引用。

拆分原因：

- 人脸算法依赖和 Java 后端依赖差异较大。
- 后续可单独升级模型。
- 人脸服务故障不会直接拖垮主业务系统。

## 3. 业务流程

### 3.1 人脸录入

1. 前台选择会员。
2. 前端打开摄像头并采集图片。
3. 后端检查会员是否可用。
4. 后端调用人脸服务检测图片质量。
5. 人脸服务提取特征并返回结果。
6. 后端保存人脸档案元数据。
7. 返回录入成功。

录入校验：

- 必须检测到且仅检测到一张人脸。
- 人脸清晰度达到阈值。
- 图片亮度不能过暗或过曝。
- 会员被冻结时不允许录入。

### 3.2 指定会员验证

1. 开始上机时选择会员和设备。
2. 前端采集当前人脸图片。
3. 后端调用人脸服务与该会员人脸特征比对。
4. 后端判断相似度是否达到阈值。
5. 写入验证日志。
6. 验证通过后允许开始上机。

### 3.3 未指定会员识别

该能力用于扩展场景，例如会员站在前台摄像头前自动识别账号。

1. 前端上传图片。
2. 人脸服务在特征库中检索候选会员。
3. 返回相似度最高的候选。
4. 后端根据阈值返回会员摘要。

## 4. 阈值建议

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 人脸质量最低分 | 70 | 低于该分数拒绝录入 |
| 指定会员验证相似度 | 0.75 | 低于该值需要人工处理 |
| 未指定识别相似度 | 0.80 | 自动识别应更严格 |
| 最大图片大小 | 5MB | 避免接口过大 |
| 支持格式 | jpg、jpeg、png | 常见图片格式 |

具体阈值需要根据实际摄像头和模型测试后调整。

## 5. 服务接口

### 5.1 录入接口

```http
POST /face-service/enroll
Content-Type: multipart/form-data
```

请求字段：

| 字段 | 说明 |
| --- | --- |
| memberId | 会员 ID |
| image | 人脸图片 |

响应：

```json
{
  "featureRef": "face/feature/1",
  "qualityScore": 86.5,
  "message": "enrolled"
}
```

### 5.2 验证接口

```http
POST /face-service/verify
Content-Type: multipart/form-data
```

响应：

```json
{
  "passed": true,
  "similarity": 0.82,
  "qualityScore": 84.1
}
```

## 6. 安全与隐私

- 人脸图片和特征属于敏感信息，必须限制访问权限。
- 默认列表页不展示人脸原图。
- 删除会员人脸档案时，应同步删除或停用特征引用。
- 人脸验证日志只保存必要结果，不保存每次验证原图，除非业务明确需要。
- 特征数据建议加密存储，密钥通过环境变量或安全配置管理。
- 人脸服务接口只允许后端主服务访问，不对公网暴露。

## 7. 异常处理

| 场景 | 处理方式 |
| --- | --- |
| 未检测到人脸 | 提示重新采集 |
| 检测到多张人脸 | 拒绝录入或验证 |
| 图片质量过低 | 提示调整光线和角度 |
| 会员未录入人脸 | 提示先录入或人工核验 |
| 相似度过低 | 验证失败并记录日志 |
| 人脸服务不可用 | 提示人工处理并记录异常 |

## 8. 开发阶段策略

第一阶段可先实现模拟人脸服务：

- 录入接口保存一条人脸档案状态。
- 验证接口返回可配置的模拟结果。
- 管理端流程先跑通。

第二阶段再接入真实模型：

- 引入 OpenCV 和人脸识别模型。
- 调整阈值。
- 增加摄像头兼容性测试。
