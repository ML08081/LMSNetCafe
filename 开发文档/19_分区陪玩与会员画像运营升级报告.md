# 分区陪玩与会员画像运营升级报告

编写日期：2026-09-02

## 1. 升级目标

本次升级围绕网咖经营场景继续细化业务能力，重点解决三个问题：

1. 机位分区不够贴近真实门店，缺少包房容量和不同区域价格信息。
2. 普通用户点单区只有基础商品，缺少陪玩、代打、游戏服务类增值业务。
3. 会员管理停留在余额和消费记录层面，缺少用户画像、流失风险和精细化运营支撑。

升级后，系统形成“前台监控机位与订单、管理员维护资源与运营、普通用户自助消费与服务”的互通闭环。

## 2. 机位分区升级

### 2.1 分区范围

设备区域调整为以下真实门店分区：

| 分区 | 区域编码 | 容量含义 | 典型用途 |
| --- | --- | --- | --- |
| 大厅A区 | `LOBBY_A` | 1 人位 | 普通散客、临时上机 |
| 大厅B区 | `LOBBY_B` | 1 人位 | 普通散客、备用机区 |
| 单人豪华包房 | `ROOM_SINGLE_LUXURY` | 1 人位 | 高端单人、安静游戏 |
| 双人包房 | `ROOM_DOUBLE` | 2 人位 | 双人开黑、情侣包房 |
| 四人包房 | `ROOM_QUAD` | 4 人位 | 小队开黑、赛事训练 |
| 五人包房 | `ROOM_FIVE` | 5 人位 | 标准五排、团队包间 |

### 2.2 数据库变化

`device_info` 新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `area_type` | `VARCHAR(40)` | 区域类型编码，用于程序筛选和统计 |
| `room_capacity` | `INT` | 机位或包房可容纳人数 |
| `hourly_rate_hint` | `DECIMAL(10,2)` | 区域展示参考小时价 |

初始化脚本已写成幂等方式，旧数据库重新执行 `scripts/init-db.sql` 时会自动补齐字段，不会重复创建表。

### 2.3 页面变化

管理员和前台设备页面已支持：

- 按大厅A区、大厅B区、单人豪华包房、双人包房、四人包房、五人包房筛选。
- 设备卡片显示区域、状态、容纳人数。
- 设备编辑时可维护区域类型、包房容量、参考小时价。
- 普通用户可在机位页面查看包房容量和价格提示。

## 3. 陪玩服务升级

### 3.1 服务分类

普通用户点单区新增陪玩服务，并沿用原来的预存网费余额支付逻辑。新增分类如下：

| 分类 | 编码 | 示例 |
| --- | --- | --- |
| 猫系陪玩 | `PLAYMATE_CAT` | FPS 枪王、MOBA 辅助指挥 |
| 犬系陪玩 | `PLAYMATE_DOG` | 上分冲锋、休闲整活 |
| 爬宠系陪玩 | `PLAYMATE_REPTILE` | 策略教学、压枪训练 |

这里的“宠物类高手代打”在系统内作为服务商品管理，用户下单后由前台在订单处理台进行匹配、服务中、完成等状态处理。

### 3.2 数据库变化

陪玩服务复用 `shop_product`、`shop_order`、`shop_order_item` 三张表：

- `shop_product.category` 保存陪玩分类。
- `shop_order.total_amount` 记录余额支付金额。
- `consume_record.consume_type = 'SHOP'` 记录消费流水。
- `member_account.balance` 实时扣减余额。

这样做的好处是饮品、零食、陪玩服务都走同一个订单和支付闭环，便于前台统一处理。

### 3.3 页面变化

普通用户服务页已支持：

- 呼叫前台。
- 饮品、零食、用品点单。
- 猫系、犬系、爬宠系陪玩服务购买。
- 使用会员预存余额直接支付。
- 查看订单处理状态。

前台服务台已支持：

- 统一查看点单和陪玩订单。
- 将陪玩订单状态显示为“准备/匹配中”“配送/服务中”等更贴近服务流程的描述。

## 4. 用户画像与精细化会员运营模块

### 4.1 画像维度

新增 `member_operation_profile` 表，为每个会员沉淀运营画像：

| 维度 | 字段 | 说明 |
| --- | --- | --- |
| 游戏偏好 | `favorite_games` | 常玩的游戏或内容类型 |
| 常用时段 | `preferred_time_slot` | 白天、晚间、深夜包夜等 |
| 饮品偏好 | `beverage_preference` | 是否偏好咖啡、能量饮料、茶饮等 |
| 消费能力 | `spending_power` | `LOW`、`MEDIUM`、`HIGH` |
| 流失风险 | `churn_risk` | `LOW`、`MEDIUM`、`HIGH` |
| 会员分层 | `segment` | 游戏发烧友、休闲追剧用户、深夜包夜用户等 |
| 运营建议 | `recommendation` | 推荐推送策略或优惠动作 |

### 4.2 优惠券设计

新增 `member_coupon` 表，用于承接流失预警和精细化运营：

| 字段 | 说明 |
| --- | --- |
| `coupon_no` | 优惠券编号 |
| `coupon_type` | 饮品券、上机代金券、包房券等 |
| `discount_amount` | 固定抵扣金额 |
| `discount_rate` | 折扣比例 |
| `min_spend` | 使用门槛 |
| `status` | `UNUSED`、`USED`、`EXPIRED` |
| `source_reason` | 发券原因，例如“14天未到店流失预警” |

### 4.3 运营逻辑

当前已实现画像数据展示与运营入口，后续可继续扩展自动任务：

1. 会员超过 14 天未上机，标记为高流失风险。
2. 高流失风险会员自动生成饮品折扣或上机代金券。
3. 根据游戏偏好、常用时段和消费能力推荐包夜、包房或开黑套餐。
4. 前台和管理员可在会员运营页面查看分层、风险、可用券和推荐动作。

## 5. 权限和角色关系

| 角色 | 本次相关能力 |
| --- | --- |
| 超级管理员 | 维护设备分区、查看会员画像、管理系统基础数据 |
| 前台人员 | 监控各区域机位、处理点单和陪玩订单、协助会员余额消费 |
| 普通用户 | 查看可用机位、呼叫前台、点餐/零食/陪玩下单、查看画像和优惠 |

三个角色仍然使用统一登录入口，登录后根据角色进入不同门户。
