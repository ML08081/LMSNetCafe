## 二、业务规则

1. 前台提供人脸核验和人工核验两种入口；人工核验需明确确认，记录为 `MANUAL`。人脸入口真实验证所选会员绑定的启用账号，失败不会开机，记录为 `FACE`。
2. 已登录的会员可以自助上机，服务端始终使用登录账号绑定的会员，不接收客户端指定的会员身份，记录为 `ACCOUNT`。会员只能预览、结算自己的会话。
3. 一个会员最多一个进行中会话，一个机位最多一个进行中会话。故障、维护、停用机位不能上机。
4. 上机前余额至少覆盖最低计费费用；上机时不提前扣款，结算时一次扣款并写消费记录、资金流水。余额不足时结算整体回滚，先充值后再结算。
5. 时长按不足一分钟进一分，再按最小时长和计费单位向上取整。金额用十进制定点运算并保留两位小数。
6. 开机时保存单价、最低时长、计费单位和预警阈值。调整或停用规则不影响已经保存快照的会话。升级前历史会话没有快照，仍使用关联规则；不能追溯还原过去未保存的价格。
7. 区域的 `hourly_rate_hint` 本次用作最低小时价。低于该价格的规则不能用于该区域；多人包房按整个包房计费，由当前会话的一个会员支付，不提供多人 AA 分账。
8. 当前计费均为按小时计算。原“包夜规则”参数实际为 50 元/小时、最低 360 分钟，最低费用 300 元，不能当成 50 元包夜套餐。新库已改为明确名称；旧库可运行下面的增量脚本更新名称。
9. 报修保留原会话；结算后存在未解决故障的设备继续为故障状态。维修完成后，存在其他故障则仍故障，有运行会话则恢复使用中，其余恢复空闲；重复维修被拒绝。
10. 上机在本项目中表示创建门店计费会话。桌宠通过轮询获取会话和提醒，不等同于远程给计算机通电、解锁 Windows 或强制锁屏。

## 三、升级现有电脑

不要为升级重新执行 `scripts/init-db.sql`。它包含演示数据写入，会覆盖部分同编号数据，只用于建立全新演示库。现有库启动新版后端时，只自动创建 `session_billing_snapshot` 新表，需要数据库账号有建表权限；已有余额和会话不会被重置。

可选增量脚本 `scripts/migrations/20261027-billing-clarity.sql` 只补充大厅 B 区计费规则，并修正原包夜规则的误导名称，可重复执行。请在当前业务库中运行；不需要修改数据库名称。

```powershell
# 项目目录中运行；安装依赖并下载校验过的模型
npm run setup
# 确认本机 .env 指向正确的 MySQL；启动服务
npm run start:lan
# 演示前检查后端、数据库、人脸模型和前端
npm run check:demo
```

旧人脸档案不能直接转换为 SFace 特征，必须在“人脸认证”页面为实际演示人员重新录入。不要删除整个特征目录或把个人照片、特征上传 GitHub。

`/api/v1/health` 会实际检查数据库和模型，返回 `DEGRADED` 表示尚未完全就绪。工作台会提示超过 24 小时的会话及使用状态异常机位；这些旧账需核对后处理，不自动清零，也不能用重跑初始化脚本来掩盖。

## 四、双电脑同步

在另一台电脑打开同一个仓库目录：

```powershell
# 拉取当前分支；拒绝覆盖已修改或分叉的本地工作；同步依赖与模型
powershell -ExecutionPolicy Bypass -File scripts/update-project.ps1 -Install
# 重启原先正在运行的服务，再启动新版
powershell -ExecutionPolicy Bypass -File scripts/start-local.ps1 -Stop
npm run start:lan
npm run check:demo
git log -1 --oneline
```

必须在两台电脑看到相同的最新提交编号，重启后才会运行新版本。此同步脚本需要手动运行；电脑离线或未拉取时，不会自动得到更新。发生分叉时脚本会停止，不会强制覆盖代码。

GitHub 同步的是代码、文档、锁定依赖和模型下载清单。`.env`、MySQL 业务数据、个人照片、人脸特征和运行日志不随 Git 同步。

如果两台电脑需要看到相同会员、余额和人脸，推荐使用一台主机运行后端、数据库和人脸服务，另一台只运行本地前端代理。摄像头电脑在 `localhost` 打开页面：

```powershell
# 把示例 IP 换成服务主机实际地址；本地前端通过代理访问同一后端
powershell -ExecutionPolicy Bypass -File scripts/dev-start.ps1 -Admin -BackendBaseUrl http://192.168.1.100:8080
# 在这台摄像头电脑的浏览器打开 http://localhost:5173/login
```

这时两台前端共享主机的数据库和人脸服务，不要同时在另一台创建独立后端。浏览器直接使用 `http://主机IP:5173` 可以查看管理页面，但摄像头通常不可用；摄像头使用本机 localhost 或正确配置的 HTTPS。浏览器 API 使用 `/api/v1` 相对地址，避免请求落到错误的本机后端。

## 五、建议演示顺序（约 8–10 分钟）

1. 展示健康检查、Git 提交编号和工作台，确认没有阻碍本次演示的环境错误。
2. 注册一个新的演示会员，充值 100 元。在“系统用户”中创建/选择绑定该会员的账号，再到“人脸认证”录入演示人员本人。
3. 重新拍摄验证本人，再用另一位在场人员验证，展示拒绝结果。退出后使用本人脸登录，并展示账号角色。
4. 前台工作台明确选择刚注册的会员、空闲大厅 A 区机位、默认 10 元/小时规则，使用人脸认证开机。不要选择仍有旧会话的 M0001 直接开机。
5. 展示机位使用中、当前费用和核验方式；重复开机应被拒绝。启动可选桌宠时，绑定同一个设备编号，观察会话与费用。
6. 点击当前会话“续费”，核对到账的是该会员；预览后结算，正常情况下最低 15 分钟消费 2.50 元，余额与流水同步变化。重复结算不能二次扣款。
7. 会员端自助选择机位和规则上机；以另一个会员身份尝试操作该会话，应被拒绝。本人下机成功。
8. 演示上机后报修→结算仍故障→维修恢复空闲；展示会话筛选和导出结果。

准备至少两个不同身份的演示人员；提前允许浏览器摄像头权限。本人重拍识别必须用现场摄像头验收，公共测试照片只能证明自动化模型链路。

## 六、测试与边界

本地自动化覆盖：会话完整生命周期、价格快照、区域价格限制、余额不足回滚、会员与机位防重、并发占位、人脸失败不创建会话、会员归属、只读角色拒绝写操作、故障修复状态、日期类型和分钟边界、异常会话诊断。人脸模型使用 OpenCV 公开样例检查本人光照变化、不同人拒绝、多人拒绝、身份歧义、旧档案和模型缺失。

GitHub Actions 增加 H2、真实 MySQL 8、人脸模型、管理端和桌宠构建检查。具体通过情况以对应提交的 Actions 结果为准。

人脸采用 [OpenCV 官方 YuNet/SFace 流程](https://docs.opencv.org/4.x/d0/dd4/tutorial_dnn_face.html)，验证阈值参考官方基线，并增加识别时的次优候选差值检查。分数是特征相似度，不是准确率或置信概率。没有完成针对门店人群的准确率标定，也没有活体检测，照片验证必须明确标注为照片验证；不能声称可防照片攻击。现场光线、摄像头权限与实际人员重拍仍需在目标电脑按上述流程验收。
